attic is designed to be self-hosted using container solutions like [Docker](https://docs.docker.com/get-started/). The Docker image is built on Alpine Linux and supports both AMD64 and ARM64 platforms, so it runs on everything from a Raspberry Pi to a cloud server.

attic requires **PostgreSQL 16+** as its database. File attachments can be stored locally or on any S3-compatible storage service.

## Using Docker Compose (Recommended)

Docker Compose is the easiest way to get attic running with all its dependencies.

**1. Create a project directory and download the configuration files:**

```shell
mkdir attic && cd attic
```

**2. Create a `docker-compose.yml` file:**

```yaml
version: "3.8"

services:
  attic:
    image: ghcr.io/lmmendes/attic:latest
    # Prepare local-storage ownership, then drop privileges before starting attic.
    user: "0:0"
    ports:
      - "8080:8080"
    environment:
      - ATTIC_PORT=8080
      - ATTIC_DATABASE_URL=postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}?sslmode=disable
      - ATTIC_LOCAL_STORAGE_PATH=/data/uploads
      - ATTIC_SESSION_SECRET=${ATTIC_SESSION_SECRET}
      - ATTIC_BASE_URL=${ATTIC_BASE_URL:-http://localhost:8080}
      - ATTIC_ADMIN_EMAIL=${ATTIC_ADMIN_EMAIL:-admin}
      - ATTIC_ADMIN_PASSWORD=${ATTIC_ADMIN_PASSWORD:-admin}
    volumes:
      - attic_uploads:/data/uploads
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-attic}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB:-attic}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-attic}"]
      interval: 5s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  postgres_data:
  attic_uploads:
```

**3. Create a `.env` file with your configuration:**

```shell
# Database
POSTGRES_USER=attic
POSTGRES_PASSWORD=change-me-to-a-secure-password
POSTGRES_DB=attic

# Session secret (generate with: openssl rand -base64 48)
ATTIC_SESSION_SECRET=change-me-to-a-random-string-at-least-32-chars

# Base URL (set to your domain in production)
ATTIC_BASE_URL=http://localhost:8080

# Initial admin credentials
ATTIC_ADMIN_EMAIL=admin@example.com
ATTIC_ADMIN_PASSWORD=change-me

# Import plugins (see /guides/import-plugins for how to obtain these keys)
# ATTIC_GOOGLE_BOOKS_API_KEY=your-google-books-api-key
# ATTIC_TMDB_API_KEY=your-tmdb-api-key
# ATTIC_BGG_API_KEY=your-boardgamegeek-api-key
```

**4. Start the services:**

```shell
docker compose up -d
```

If everything completed successfully, attic should now be running at [http://localhost:8080](http://localhost:8080). Log in with the admin credentials you configured in the `.env` file.

## Kubernetes

The image defaults to numeric UID and GID `1000:1000`. It also supports other non-root identities assigned through `runAsUser` and `runAsGroup`. When started as non-root, the entrypoint keeps that identity and does not change storage ownership or switch users.

This pod-spec fragment shows the security settings for Kubernetes' Restricted Pod Security Standard:

```yaml
spec:
  securityContext:
    fsGroup: 1000
    fsGroupChangePolicy: OnRootMismatch
  containers:
    - name: attic
      image: ghcr.io/lmmendes/attic:latest
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 1000
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
        seccompProfile:
          type: RuntimeDefault
```

Add your database configuration and, for local storage, a writable volume mounted at `/data/uploads`. Adjust the IDs to your cluster's policy. Leave `ATTIC_PUID` and `ATTIC_PGID` unset; if explicitly configured for local storage, both must match the container's runtime UID/GID or startup fails.

For supported volume types and CSI drivers, `fsGroup` provides group access to mounted storage. Otherwise, provision volume permissions separately. The image's directory ownership does not apply to a volume mounted over that directory. An uploads volume and `fsGroup` are unnecessary when using S3 storage. See [Kubernetes volume permissions](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/#configure-volume-permission-and-ownership-change-policy-for-pods).

## Initial Setup

On first startup, attic automatically runs database migrations and creates an initial admin user using the `ATTIC_ADMIN_EMAIL` and `ATTIC_ADMIN_PASSWORD` environment variables. The defaults are `admin` / `admin` if not specified.

After starting attic for the first time:

1. Open the application in your browser (default: [http://localhost:8080](http://localhost:8080))
2. Log in with your admin credentials
3. **Change the default password immediately** if you used the defaults

You can also reset a user's password via the CLI:

```shell
# Docker Compose
docker compose exec attic /app/attic --reset-password --email admin@example.com --new-password your-new-password

# Docker
docker exec -it attic /app/attic --reset-password --email admin@example.com --new-password your-new-password
```

## Upgrading

To upgrade to a new version of attic:

**Docker Compose:**

```shell
docker compose pull
docker compose up -d
```

**Docker:**

```shell
docker pull ghcr.io/lmmendes/attic:latest
docker stop attic
docker rm attic
# Run the same docker run command you used for the initial installation
```

Database migrations run automatically on startup, so no manual migration step is needed.

### Upgrading to the non-root image

The image now starts as `1000:1000` by default. Before upgrading, ensure existing local-storage volumes and bind mounts are writable by the selected UID/GID. Non-root startup does not repair ownership, and existing files retain their permissions.

If you previously relied on the entrypoint to prepare ownership, use the root-start Docker setup below or provision permissions separately. In Kubernetes, keep non-root startup and configure volume access through your storage provider and security context.

## File Permissions (PUID/PGID)

For local storage, the image runs as `1000:1000` by default. To use another identity, either start directly as that user with writable storage, or start the entrypoint as root so it can prepare the storage directory and drop privileges.

```shell
# Find your user/group IDs
id -u  # PUID
id -g  # PGID
```

For root-start ownership setup, merge these settings into the attic Compose service, replacing the example IDs with your host user's IDs:

```yaml
services:
  attic:
    user: "0:0"
    environment:
      - ATTIC_PUID=1000
      - ATTIC_PGID=1000
```

The Compose example above already includes `user: "0:0"`. For standalone Docker, add `--user 0:0` and both environment variables. The entrypoint changes ownership of the storage base directory, then runs attic as the requested UID/GID (or `1000:1000` when unset). It does not recursively change existing files. This mode requires permissions to change ownership and switch users; use non-root startup when dropping all capabilities.

To start directly as non-root, use Compose `user: "2000:2000"`, Docker `--user 2000:2000`, or Kubernetes `runAsUser`/`runAsGroup`, and leave PUID/PGID unset. Storage must already be writable by that identity. If you do set PUID/PGID for local storage, set both to non-negative integers matching the runtime UID/GID; a missing partner or mismatched identity causes startup to fail.

## Health Checks

The Docker image includes a built-in health check that polls the `/health` endpoint every 30 seconds. You can verify attic is running correctly:

```shell
# Check container health status
docker inspect --format='{{.State.Health.Status}}' attic

# Or call the endpoint directly
curl http://localhost:8080/health
```
